# 羽化寬度：買得到幾何對齊，代價是把預算羽化掉一半以上

**尚未進入 `docs/RESULTS.md`**，等使用者裁定。

`scripts/carrier_feather_tradeoff.py`。十張影像 × 六個羽化寬度 × 三個內容形式
× 四個算子。純 CPU、未最佳化。

## 為什麼有這一份

`runs/registration_ceiling/` 與 `runs/polar_carrier/` 都收在同一句話上：
幾何那一欄剩下的損失**在支撐邊界上**，與內容場的參數化無關。
而支撐邊界是**載體的幾何**，`--carrier-feather` 就是它的旋鈕。

## 三件這張表說了的事

**一、羽化確實買得到對齊，而且是單調的。** 由 0 到 64：帶限的旋轉 +0.72 →
+0.80、裁切 +0.51 → +0.60；半徑場的旋轉 +0.79 → +0.86。
邊界項是真的，而且動得到。

**二、代價是預算，而預算正是本專案的主張。** 同一段路上加權面積由 0.249
掉到 0.096（**−61%**）、RMS 由 0.203 掉到 0.092（**−55%**）。
`runs/purifier_transfer/` 第二節量過振幅對存活的影響比頻帶還大
（週期 4 px 上 RMS 0.20 過 jpeg30 留 0.681，RMS 0.01 留 0.008），
而 `docs/DIRECTION.md` §1 的主張是「在免費的失真上把預算開大」。
**羽化到 64 等於把主張反過來做。**

**三、極座標的構造在裁切上比重羽化划算。** `g(φ)` 在**羽化 0**（RMS 0.212）
拿到的裁切對齊是 **+0.64**，已經高於帶限 S=32 羽化到 64（RMS 0.092）
的 +0.60——**同一件事，一個花掉一半以上的預算，一個沒花。**
`f(r)` 在旋轉上同型：羽化 0 的 +0.79 對帶限羽化 48 的 +0.80。

**但兩個構造換掉的是不同的一半**：`f(r)` 在裁切上是 +0.41，比帶限的 +0.51
**更差**；`g(φ)` 在旋轉上與帶限持平。不可以同時宣稱兩邊。

## 沒有被回答的

**效果讀數。** 這裡量的全部是訊號存活，不是防禦有沒有效。羽化縮面積、
極座標砍自由度，兩者都可能讓效果掉，而那要 GPU。
依 `CLAUDE.md`「訓練方法的實驗：不設判準」，**本表不決定該用哪個寬度**。

**兩種讀法。** `align` 是「沒有人替它對回位」的讀法。抗淨化的正式量測對
幾何類算子用 `reference=purified_orig`（兩側吃同一個變換），在那個讀法下
既有資料是好的：`crop_resize0.1` 保留率中位 0.99。兩種都要報。

## 一個踩過的坑

第一版把支撐轉成布林（`sup > 0`）再交給 `render`，於是**六個寬度的加權面積
全部是 0.249、每一列的讀數逐位元相同**——羽化帶被整條算成滿的，掃描完全
沒有作用而表面上一切正常。軟支撐必須原樣傳下去。
