### 2.1 `lr_probe.csv` 遺漏 `diverged` 欄

`align` 的發散有兩條路：第 0 步就發散時 `raise_if_diverged` 拋 `Diverged`
（由 except 記下），迴圈中途出現非有限值時則是 `break` 記一列 history 後
**正常返回**——還原最佳步的 φ 之後 `x_align` 仍可用，拋例外是錯的。

`_probe_align_lr` 的正常返回路徑不看 history 的 `diverged`，於是第二條路的
候選只留下 `final_loss=inf` 與 `finite=False`。而 `write_csv` 取全部列的鍵
**聯集**，沒有任何一列帶該鍵，整欄就不存在。

`_probe_lr` 的正常返回現在也明寫 `diverged=False`：省略時該欄只在恰好有
候選發散的批次裡出現，讀 CSV 的人無法分辨「沒有候選發散」與「這一欄根本
沒被寫出來」——b3 的 `lr_probe.csv` 正是後者。

### 2.2 mist 與 dia_r 在 1024² 下 OOM

**不是跨格累積。** OOM 訊息報「23.14 GiB is allocated by PyTorch」對
「26.89 MiB reserved but unallocated」，即**活著的張量**而非快取碎片；且在
全新行程中單獨跑 mist 同樣失敗（`b3_bird_03/diag_mist.log`，`done=0 failed=1`）。
`empty_cache()` 幫不上忙。512²／SD v1.4 的同一格則正常跑完（v14 三張圖
`done=7 failed=0`），故這是 1024² 專屬的容量問題。

`1024633` 曾為 dia_r 包過 UNet 前向，但**沒有包 VAE**。本次的 dia_r OOM 位置
是 `sd.vae.decode`（Tried to allocate 256.00 MiB）。DIA-R 的圖上除了 20 次
已 checkpoint 的前向，還有一次 VAE 編碼與一次 VAE 解碼，1024² 下兩者的中間
激活同時留存。兩者都取確定性的值（編碼是 `.mode()`、解碼是純函式），重算
逐位元相同，故可安全 checkpoint。

mist 的 fused mode 把**兩次** VAE 編碼與一次完整 UNet 前向放在同一張圖上，
而 `baseline_kwargs` 從未給它任何 checkpoint 設定。只包 UNet 之後仍在同一
位置 OOM（`diag_fix.log`），故那兩次 VAE 編碼才是主導項——1024² 下 VAE
編碼器最外層一張激活即 1024²×128×2 B = 268 MB。

**取樣的 VAE 編碼不能直接包 checkpoint。** `latent_dist.sample(generator)`
用的是呼叫端持有的顯式 `Generator`，而 `use_reentrant=False` 保存的是
**預設** RNG 狀態，管不到它；重算會再抽一個樣本，反向傳播算的梯度因此屬於
另一個函式——沒有任何症狀的數值汙染。作法是把噪聲抽在區塊外、區塊內做
`mean + std·eps`。diffusers 0.39.0 的 `sample()` 逐字為

```python
sample = randn_tensor(self.mean.shape, generator=generator,
                      device=self.parameters.device,
                      dtype=self.parameters.dtype)
x = self.mean + self.std * sample
```

以同一個 `randn_tensor`、同一組 (shape, generator, device, dtype) 抽噪聲，
產生的樣本與抽樣順序都與原路徑逐位元相同，而重算因 eps 已固定成為確定性。
DIA-PT 的 `_encode_pt` 同樣走 `.sample()`，未套用——該變體本來就不在本輪
格點內（`grid.EXCLUDED`）。

重算數值中性，故兩個開關都不進 `config_hash`，與 `1024633` 對 `unet_ckpt`
的處理一致。

### 2.3 `shard.sh` 的 `[exit 0]` 掩蓋失敗

`cmd || break` 之後的 `$?` 取的是 `break` 自己的 0。當日兩次失敗
——b3_bird_03（train 兩格 OOM）與 v14_cat_02（rayscale 一格失敗）——的 log
尾端都是 `[exit 0]`，而 `watch_remote.sh` 依 `[exit` 判定收工，於是把失敗
回報成「收工」。這是最貴的一種誤報：輪詢的一方會停止關注。

改為自行記錄失敗的段與真正的退出碼（`[fail-stage <段> rc=<碼>]`）。
`$?` 也不能寫在 `if ! cmd` 之後——`!` 會把狀態反相。

### 2.4 生成路徑下限是全域常數（本日影響最大的一項）

`grid.generative_floor_skip` 用 `GENERATIVE_LPIPS_FLOOR = 0.1434` 判斷哪些
τ 對走生成路徑的條件結構上不可達。但該下限**逐影像差很多**：

| 影像 | v14 下限 LPIPS | τ=0.20 可達？ |
|---|---|---|
| bird_03 | 0.1330 | 可 |
| **cat_02** | **0.2398** | **不可** |
| dog_03 | 0.1403 | 可 |

於是 `rayscale/N3/cat_02/tau0.2` 被排為可跑，`solve_k` 二分 28 次後正確地
拒絕（k 已推到 3.7e-09，LPIPS 仍停在 0.2388）並拋出，該格記為 `failed`，
**整個分片就此停住**。v14_cat_02 與 b3_cat_02 都卡在這裡。

這與 2026-08-06 第 8 號缺陷（門檻是一個不可達的全域常數）是同一個型態：
一個對「平均影像」成立的常數，套到個別影像上就不成立。

修法是真跑時在 `build_resources` 之後量測逐影像下限並重建格點

之前回答「這次要跑多久」），兩者的理由字串刻意不同，報表看得出依據的是
量出來的數字還是一個常數。

**`skip_reason` 不進 `config_hash`**：它是排程資訊不是設定。實測驗證
（v14_cat_02 續跑時 `train: resumed=7`），兩個批次已算完的上千格全部保留。

cat_02 在 τ=0.35 仍高於其下限，故 N3/cat_02 在該點照常貢獻資料。

## 5. τ=0.20 上兩道 hinge 的實測（待裁決事項的資料）

以 `local_acutance_dev(x_base, x_def)` 與 `local_chroma_bias(x_base, x_def)`
逐格重算——即兩道 hinge **實際比對的那兩個量**，不是 `grid.csv` 的
`fid_acutance_ratio`（那是銳利度比值，定義不同）。參照對象與
`objective.fidelity_term` 一致：像素路徑為原圖，生成路徑為 `G(x; φ=0)`。

| 條件 | 類別 | acut_dev（bird / dog） | 超過 0.04？ |
|---|---|---|---|
| N1 | 非加性 | — / 0.0525 | 是 |
| N2 | 非加性 | 0.0553 / 0.0411 | 是 |
| N3 | 非加性 | 0.1411 / 0.1380 | 是（3.5 倍） |
| R | 隨機對照 | 0.0864 / 0.0698 | 是 |
| PhotoGuard-c | 加性 | 0.0152 / 0.0080 | 否 |
| Mist | 加性 | 0.0341 / 0.0422 | 否／勉強是 |
| DIA-R | 加性 | 0.0186 / 0.0279 | 否 |

**在匹配的 LPIPS 下，非加性條件的鈍化偏差是加性 baseline 的 2–9 倍**，而
R（純隨機位移場、未經任何最佳化）同樣高。故這不是最佳化把影像弄糟，而是
**位移場這個參數化在同一個 LPIPS 上就會產生這麼多局部銳利度變化**。門檻
0.04 落在非加性條件的分佈中間，等於一道只對我方啟動、對 baseline 從不啟動
的懲罰。

`tau_chroma = 0.8` 則對 N1／N2／R（0.32–0.47）幾乎是死的，對 N3
（**2.60–2.73**，超過門檻 3 倍）壓倒性；乘上 `gamma_chroma = 100` 即約 190
的常數懲罰。

### 5.1 §10.3 的結論被推翻

`RESULTS_2026-08-06` §10.3 記載位移場是「變銳利」（比值 1.023→1.075），
並據此說對稱的 `|r−1|` 罰錯了方向。τ=0.20 的實測顯示方向**由影像決定**：

| | bird_03 | dog_03 |
|---|---|---|
| N2 銳利度比 | **0.9882（變模糊）** | 1.0132（變銳利） |
| N3 銳利度比 | **0.8985（變模糊）** | 1.0034 |

兩個方向都真的會發生，故對稱性本身不是缺陷。真正的問題是門檻的**量級**。

### 5.2 建議的形式（待裁決）

`acut_dev / τ` 在同一條件下近乎常數：

| bird_03 N2 | τ=0.05 | 0.10 | 0.20 | 0.35 |
|---|---|---|---|---|
| acut_dev | 0.0180 | 0.0311 | 0.0553 | 0.1167 |
| acut_dev / τ | 0.36 | 0.31 | 0.28 | 0.33 |

既然比值大致固定，一個在 τ=0.05 上定出的絕對值用到 τ=0.20 就自動變成四倍
嚴。故建議改為正比於訓練點：

```
tau_acut   = 0.8 × τ_train    → τ=0.20 時 0.16（原值 0.04 = 0.8 × 0.05）
tau_chroma = 16  × τ_train    → τ=0.20 時 3.2 （原值 0.8  = 16  × 0.05）
```

錨點是使用者在 τ=0.05 上的原判讀，不是新編的數字。該規則同時重現兩次
人眼判讀：τ=0.20 時無條件觸發（N3 最高 0.141 < 0.16），τ=0.35 時 N3 的
0.343／0.355 仍觸發——那正是 §10.1 判為「明顯壞掉」的點。

兩者都在 `loss_params` → `config_hash`，改動需新批次。

## 6. 對齊指標的限制（待裁決）

在 LPIPS 精確等於 0.20 這一點上，`acut_dev` 的跨度是 0.008（PhotoGuard-c）
到 0.141（N3），**17 倍**。「匹配失真」在非 LPIPS 的軸上完全不成立。

LPIPS 建在帶 pooling 的深度特徵上，該結構**設計上就對小幾何形變不敏感**，
故位移場在同一個 LPIPS 下人眼看起來更明顯。它現在在那裡的理由是
`DESIGN` §3.2 要求匹配失真比較，且基準論文與這條線的文獻都用 LPIPS。

四個替代方案，依建議順序：

| | 方案 | 成本 |
|---|---|---|
| (d) | **不對齊，報整條取捨曲線**——防禦效果對每個保真軸各一條，比較曲線而非單點 | 接近零，四個 τ 點已在跑 |
| (b) | 同一組結論在兩種對齊下各報一次（LPIPS 一次、對幾何敏感的 FSIM 或 1−SSIM 一次） | 多一輪段 2＋段 3 |
| (a) | 改對「交集」對齊，與段 1 的目標函數一致 | 各條件停在不同 LPIPS，失去乾淨的軸 |
| (c) | 2AFC 人眼錨定 | 唯一名副其實，但需使用者的時間 |

建議 (d) 作主要呈現、(b) 作穩健性檢查。

## 6a. 段 3 的結果：防禦效果全部在雜訊裡

四個分片（v14 的 bird_03／dog_03、b3 的 bird_03／dog_03）各 980 格、零失敗，
結論一致。以 v14_bird_03 為例，τ=0.20、identity 下的 `effect_siglip`：

| 條件 | N1 | N2 | N3 | R | PhotoGuard-c | Mist | DIA-R |
|---|---|---|---|---|---|---|---|
| 平均 | −0.0037 | +0.0013 | −0.0039 | −0.0057 | −0.0074 | −0.0028 | −0.0050 |

參照尺度：bird_03 的 prompt 是 `a butterfly`，原圖對它的 SigLIP 是 0.0048，
未防禦編輯後升到 0.1054。**攻擊可用的區間是 0.100，所有防禦收回的是 ±0.005。**

`purify_advantage.py` 因此拒絕出表——`retention` 是效果的比值，分母近乎零時
整個判定沒有定義。那是該腳本的閘門在做它該做的事，不是資料不完整。

### 6a.1 人眼與指標一致

| | τ=0.35 的編輯輸出 |
|---|---|
| 未防禦對照 | 鳥 → 蝴蝶，乾淨 |
| N2 | 鳥 → 蝴蝶，乾淨，畫質甚至更好 |
| N3 | 鳥 → 蝴蝶，乾淨 |

## 6b. 為什麼 baseline 也失效：不是預算，是威脅模型

### 6b.1 匹配失真協定把 baseline 壓到原始設定以下

段 2 把每個條件縮放到 LPIPS = τ。三篇加性方法**原生就運作在更高的失真上**

| PhotoGuard-c | 0.4025 | 0.469（47%） |
| DIA-R | 0.2972 | 0.594（59%） |
| N2 | 0.0666 | 2.500（放大 2.5 倍） |
| N3 | 0.1348 | 6.500（放大 6.5 倍） |

與量到的 `fid_linf = 0.011` 吻合。

### 6b.2 但縮小不是失效的原因——原始強度下同樣無效

`scripts/diag_native_strength.py` 以段 1 的 `x_def.png`（k=1，未縮放）重跑評測，
走與 `eval_executor` 完全相同的路徑：

|---|---|---|---|
| Mist | 0.6212 | **+0.0014** | 0.0104 |
| PhotoGuard-c | 0.4015 | **+0.0006** | 0.0179 |
| DIA-R | 0.2969 | **−0.0034** | 0.0086 |

**Mist 在 LPIPS 0.62 下效果仍是零。** 故問題不在預算。

### 6b.3 判準比原作嚴——用它們自己的判準，我們重現了

`edit_lpips`（防禦後的編輯輸出離未防禦編輯多遠，多數 baseline 論文用的判準）：

| 條件 | st=0.2 | 0.4 | 0.6 |
|---|---|---|---|
| Mist | 0.686 | 0.711 | **0.723** |
| PhotoGuard-c | 0.497 | 0.545 | **0.574** |

| N2 | 0.101 | 0.127 | 0.220 |
| R | 0.048 | 0.069 | 0.156 |

Mist 把輸出改動了 LPIPS **0.72**——那是一張完全不同的圖，它們的論文用這類
指標報告成功是有依據的。但那張圖**仍然是一隻蝴蝶**：本專案的判準是

### 6c.1 低 strength 端是量測假象，不可用

strength 0.2–0.3 時 Mist（−0.018）與 DIA-R（−0.045）為負，即「防禦後反而
更像 prompt」。原因是編輯幾乎不動，對照側 ≈ 原圖（一隻鳥，對「a butterfly」
對齊很低），而防禦側是重度失真的圖，失真破壞了「鳥」的辨識度使 SigLIP 給了
更高分。**這一段的數值不可用於任何判定。**

## 10. 下一批改為 inpainting 威脅模型（使用者 2026-08-07 定案）

### 10.1 為什麼

1. **strength 這個自由度會消失。** 五篇 baseline 的原始碼**都沒有**
   attack-time strength：PhotoGuard 的 `attack_forward` 由 `torch.randn`
   起跑（cell 10 的 `strength=0.7` 被賦值但未傳入 `super_l2`）、AdvPaint 取
   inpainting pipeline 預設排程的 `timesteps[0]`、PromptFlare 的 latent 不經
   strength、Mist 的 t ~ U(0,1000)、DIA 走固定 10 步 DDIM 軌跡。0.6 是本專案
   自己定的，而 §6c 顯示它選在防禦方最無力的一端。inpainting 沒有這個參數。
2. **三篇回到原生形式。** PhotoGuard-c、AdvPaint、PromptFlare 原作**就是**
   inpainting，目前全部標著 `modified_from_paper=True`，而改動的性質是
   「梯度從哪條路進入計算圖」。
3. **防禦方重新有著力點。** inpainting 時未遮罩區域是直接給模型的，生成
   內容必須與脈絡一致；防禦擾動污染的是脈絡。全圖 img2img 在 strength 0.6
   下模型可整張重畫，不必保留任何原內容。

### 10.3 幾個必須記住的設計點

**遮罩來源**：由模型自己對資料集宣告的 `content` 詞的 cross-attention 產生，
即 Lo et al. 式 (3)(4)（`attention.py` 既有、`test_lo_protocol.py` 已釘住）。
`lo_aligned` 沒有標註遮罩，PIE-Bench 的取不到（連不上 HF）。附形態學閉運算
與外接矩形：注意力閾值會留下孔洞，而人工畫的遮罩不會，那些孔洞造成的斑點
是假陽性的來源。

**`--mask-mode` 沒有預設值**。`config_hash` 吃整個 `base_config`，多一個鍵
就改變**每一格**的雜湊；無條件加入會讓 img2img 的既有批次一旦續跑就全部
作廢。故 `mask` 鍵只在 inpainting 時出現，並由測試釘住 img2img 的雜湊不變。

**兩個旗標不可互相代替**：

| | `needs_mask`（原作的攻擊需不需要遮罩） | `grad_outside_mask`（原始碼有沒有把梯度乘 (1−mask)） |
|---|---|---|
| PhotoGuard-c | False | **True** |
| AdvPaint | **True** | False |
| PromptFlare | **True** | **True** |

前兩篇在這一對上取值相反，用錯會對錯的論文施加梯度遮罩且沒有症狀。

**一個修掉的靜默缺陷**：AdvPaint 的 `_forward_and_record` 原本從 `ctx_like`
讀遮罩，而 GT 那次呼叫傳的是 `None`——GT 會走 img2img、迭代走 inpainting，
兩組 Q/K/V 相減量到的是路徑差異而不是擾動效果，而損失曲線照樣會下降。
改為顯式參數。

### 10.4 未查證的一項

AdvPaint 的 `masked_image_latents` 取 sample 還是 mode，既有的逐行紀錄沒有
載明。目前跟隨 `z0` 與 diffusers 的 `retrieve_latents` 取後驗抽樣。兩者差
一個 std·ε 項，會改變損失數值但不改變梯度所走的路徑。取回原始碼後須確認。
