### 2.2 根因（三層，只有第二層是我們的缺陷）

1. **威脅模型的 strength 選錯點。** 攻擊的區間在 0.5 就飽和，防禦效果在
   0.4 之後崩掉；0.4 是唯一同時滿足兩者的點，而我們定在 0.6。段 0 的
   `calibrate_strength` 取「編輯效果最大」，**由建構上就會選到防禦最無力的
   一端**——其 docstring 早已預告這件事。
2. **訓練被 `tau_acut = 0.04` 綁死。** 六個訓練格的 `fid_acut` 全部精確頂在

### 3.4 三個不要重新踩的設計點

**`--mask-mode` 沒有預設值。** `config_hash` 吃整個 `base_config`，多一個鍵
就改變**每一格**的雜湊。故 `mask` 鍵只在 inpainting 時出現，img2img 的雜湊
逐位不變（有測試釘住）。

**兩個旗標不可互相代替**：

| | `needs_mask`（原作的攻擊需不需要遮罩） | `grad_outside_mask`（原始碼有沒有把梯度乘 (1−mask)） |
|---|---|---|
| PhotoGuard-c | False | **True** |
| AdvPaint | **True** | False |
| PromptFlare | **True** | **True** |

前兩篇取值相反，用錯會對錯的論文施加梯度遮罩且**沒有症狀**。

**訓練期與評測期必須是同一種攻擊。** `optimize` 的代理編輯鏈原本直接呼叫
`sdedit`，在 inpainting 下會變成「防禦對著 img2img 最佳化、評測跑 inpainting」，
兩者在報表上都叫「編輯」、數字也都合理。現在兩條鏈都走 `edit`，有原始碼檢查釘住。

### 3.4a 起跑前必須先處理：約束會在到達預算之前就擋下我們的方法

**這是第二階段最可能重演第一階段失敗的地方，於 2026-08-08 事前查出。**

#### 為什麼 inpainting 救不了這件事

`L_fid` 的四道 hinge 比的是 `x_def` 對 `x_base`，而位移場的 `pixel_residual`
是純 `grid_sample`、**不經過模型**，像素路徑的 `x_base` 就是原圖。也就是說
**`L_fid` 的計算裡沒有任何一項與「攻擊是 img2img 還是 inpainting」有關**。
第一階段那個「訓練被 `tau_acut` 綁死」的問題會原封不動搬過去。

由 `runs/tau_threshold_probe_v14.csv` 線性內插，各條件的 `acut` 撞到 0.04
時的 LPIPS：

| 影像 · 條件 | acut=0.04 的 LPIPS | 綁定的是 |
|---|---|---|
| bird_03 · R | **0.066** | `tau_acut` |
| bird_03 · N1 | **0.106** | `tau_acut` |
| bird_03 · N2 | **0.137** | `tau_acut` |
| dog_03 · R | **0.092** | `tau_acut` |
| dog_03 · N1 | **0.149** | `tau_acut` |
| dog_03 · N2 | **0.193** | `tau_acut` |
| N3（兩張圖） | 在 τ=0.20 已是 0.138–0.141（**3.5 倍**） | `tau_acut`，更早 |
| **PhotoGuard-c** | 到 τ=0.35 都沒撞到 | **`tau_lpips`，拿到完整預算** |

五個非加性條件全部在 **0.066–0.193** 撞牆，而主表在 0.20。加性 baseline 不受
這道約束——`acut` 量的是局部銳利度偏差，位移場天生產生它，加性雜訊不會。

#### inpainting 另有一個第一階段沒有的問題：遮罩讓我們白付預算

inpainting 下防禦方的著力點**只在未遮罩的脈絡**（遮罩內攻擊方會整片覆寫）。
但目前：

- 位移場**對整張圖生效**，包括遮罩內（`site_warp` 與 `objective` 都
  **完全不知道遮罩的存在**，已查證）；
- `L_fid` **對整張圖收費**；
- 故遮罩內的擾動 = **零防禦價值 + 全額保真成本**。

而 PhotoGuard-c 與 PromptFlare 的原始碼**本來就把梯度乘 `(1 − mask)`**
（已忠實實作為 `grad_outside_mask`），一分預算都不會花在那裡。遮罩涵蓋率
若為 0.3，我們等於先丟掉三成預算才開始比賽——**而那是它們論文的設計，
不是我們的 bug**。

#### 兩個處置（需使用者裁決，兩者都進 `config_hash`）

**A. 門檻改為正比於 τ**

```
tau_acut   = 0.8 × τ_train    → τ=0.20 時 0.16
tau_chroma = 16  × τ_train    → τ=0.20 時 3.2
```

錨點是使用者在 τ_lpips=0.05 上的原判讀（0.04 = 0.8 × 0.05）。該規則同時
重現兩次人眼判讀：τ=0.20 時無條件觸發，τ=0.35 時 N3 的 0.343／0.355 仍
觸發——正是 `RESULTS_2026-08-06` §10.1 判為「明顯壞掉」的那一點。
**不改的話第二階段會重演第一階段。**

**B. 位移場在遮罩內歸零**

`site_warp.displacement` 乘上 `(1 − mask)`，防禦根本不去動攻擊方會覆寫的
區域。這是最貼近 PhotoGuard／PromptFlare 原生作法的形式，做完之後
「非加性 vs 加性」才真正對等——目前我們是在一個自己造成的劣勢下比賽。

實作小（`site_warp` 加一個可選遮罩、`build_module` 傳進去），但改變
`module_params` 因而進 `config_hash`；本來就是新批次，無額外成本。

> **若只做 A 不做 B**：訓練跑得到預算上限，但仍有約遮罩涵蓋率比例的預算
> 花在無效區域。若兩者都不做：預期第二階段再次得到「量不到效果」，七小時
> 機時白花。

### 3.5 尚未做的

- **段 0 的 `calibrate_strength` 在 inpainting 下退化為單點**（攻擊強度由
  遮罩面積決定）。行為正確，但 `STRENGTH_GRID` 的掃描變成純浪費，應改為
  量**遮罩面積**的影響——那才是 inpainting 的攻擊強度軸。
- **`purify_advantage.py` 的判準在 inpainting 下要重新確認**：它依
  `retention_usable`（`mean ≥ 3σ`）篩選，若第二階段仍然量不到效果，
  同樣會拒絕出表。那時要看的是 §6c 那種 strength／遮罩面積掃描，不是硬跑格點。
- **inpainting 的 `warp_max_disp` 尚未校準**。段 0 的 `warp_reach` 會量，
  但 512² inpainting 的可達 LPIPS 未知，可能需要調整。
- **`tau_acut` / `tau_chroma` 的門檻**仍是 τ=0.05 上定出的絕對值。建議改為
  正比於 τ（`0.8 × τ`、`16 × τ`，錨點是使用者在 τ=0.05 的原判讀），見
  `RESULTS_2026-08-07` §5.2。兩者都在 `config_hash`。
- **AdvPaint 的 `masked_image_latents` 取 sample 還是 mode 未查證**
  （`RESULTS_2026-08-07` §10.4）。目前取後驗抽樣。
