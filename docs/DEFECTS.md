# 缺陷

每一筆自足：症狀、根因、處置、釘住它的測試。

**共通型態**：本專案反覆出現的失敗是「跑起來很正常、數字也合理，
只是量到的不是要量的東西」。凡是沒有硬症狀的缺陷，處置一律附一條測試。

- **來源**：EXP-b1

## DEF-007 · 段 3 的產物在 τ 之間互相覆寫

## DEF-008 · `unet_ckpt` 被當成注意力前向的開關

- **症狀**：EXP-s3a 段 0 首次起跑即 OOM（23.42 / 23.56 GiB），
  死在 `_probe_align_lr` ——**保真對齊**那一步，根本不碰注意力目標
- **根因**：`ConditionSpec.unet_ckpt` 只管生成／編輯路徑。
  注意力 hook 與 checkpoint 不相容那件事，擋它的是 `_build_attn_step` 裡
  不傳 `use_ckpt` 的 `sd._eps(...)`，是寫死的。
  對 site warp 那個旗標是**空轉**的（`gen.generate` 直接回傳 `pixel_residual`，
  不碰 UNet），照抄到 site apa 就關掉了 10 步可微去噪鏈的 checkpoint
- **處置**：MTH-N4 改回 `unet_ckpt=True`
- **測試**：`test_注意力前向恆不checkpoint且與unet_ckpt旗標無關`（AST 檢查）、
  `test_走生成路徑的條件必須開checkpoint`

## DEF-009 · `class_margin` 每格只取一個 τ，且 metadata 取另一個 τ

- **症狀**：**數字看起來完全合理**。CSV 的 `tau` 欄全錯，而 margin 值反而是對的
- **根因**：`edit_pngs` 以 seed 為鍵、逐 τ 互相覆寫，留下字串排序最大的那個；
  `meta_for` 取排序**第一個** metrics 檔。兩者於是配到不同的 τ
- **為什麼難察覺**：挑中的**恰好**是最大的 τ（"0.5" 在 "0.35" 之後），
  也就是主表那一點——正確性建立在字串排序的巧合上，τ 若含 0.55 與 0.6 就會挑錯
- **處置**：逐 (seed, τ) 各一列，metadata 依 τ 配對，摘要逐 τ 分開
- **測試**：`tests/test_class_margin.py`，其中一條刻意用 0.5/0.55/0.6 這組 τ

## DEF-010 · `eval_protocols` 的 τ 寫死成第一階段的軸

- **症狀**：EXP-s3a（τ_train 0.50）的報表印出四張看起來正常的表，
  **沒有一張是主表那一點**
- **根因**：`--taus` 預設 `[0.05, 0.1, 0.2, 0.35]`；ISR 段對整份 margin 檔
  一次算完、不分 τ
- **處置**：τ 由 `grid.csv` 實際出現的值導出；ISR 逐 τ 分列

## DEF-011 · inpainting 的遮罩與 `c_a` 位置關係做反了

- **症狀**：尚未量到。**結構上**使 inpainting 的防禦無處施力
- **根因**：Lo et al. Figure 3 的遮罩是攻擊方要重畫的區域，`c_a` 是**遮罩外**
  那個要保住的物件（圖說：底線的詞即要免疫的內容，而底線在遮罩外的 corgi）。
  我方的 `masks.py` 由 `c_a` 產生遮罩，兩者重疊
- **後果**：式 (4) 的 M 落在會被整片覆寫的區域；而 `--warp-mask-gate`
  又把擾動推到遮罩外——損失看的地方與擾動所在的地方不相交
- **為什麼三批都沒有症狀**：遮罩產得出來、涵蓋率印得出數字、格點全部
  `done`。缺的不是任何一段計算，而是「這兩塊區域不可以相交」這道檢查
- **處置**（DEC-010 + DEC-012）：分兩層。
  1. **遮罩改為人工繪製**（`scripts/draw_masks.py`），不再由任何一個詞的
     注意力產生。畫的人看得見主體在哪裡，「把 c_a 留在遮罩外」因此是一個
     直接做得到的動作。
  2. **式 (5) 只計算 M 落在遮罩外的部分**（`restrict_outside_mask`）。
     遮罩內的格點在這個威脅模型下承載不了防禦——`mask_latents` 做
     `encode(x_def * (1 - mask))`，那些像素在進入模型之前就被歸零。
- **為什麼不是「斷言兩者不相交」**：那是本缺陷第一次的處置，實測**不可
  滿足**。Lo Figure 3 要求的是 c_a 這個**物件**在遮罩外，而 M 是它的
  **注意力圖**，cross-attention 本來就瀰漫。三張影像的 M 有 9.6%／24.7%／
  17.6% 落在遮罩內，保護帶加到 81 px、`attn_mask_tau` 加到 0.9 都降不到零
  （數據見 DEC-012）。把 c_a 的注意力圖與 c_a 這個物件當成同一件事，
  是本缺陷的第二層——第一層是遮罩與 M 同源。
- **中途的一版**：曾改由 `prompts[1]` 的新增物件詞產生遮罩並扣掉 c_a 的
  保護帶。那條路自帶問題——該物件在原圖裡不存在，注意力會落在畫面中最像
  它的東西上——已隨 `edit_region` 欄位一併移除
- **測試**：`tests/test_inpaint.py` 的 `test_遮罩內的格點不計入式5`、
  `test_限制以max_pool保守排除`、`test_遮罩外幾乎沒有M時拋出`、
  `test_缺遮罩檔時拋出且不落回自動產生`、`test_空遮罩與填滿的遮罩都拒收`

## DEF-012 · `shard.sh` 寫死 `$HOME/WACV`，且 `env.sh` 會把工作目錄換回去

- **症狀**：EXP-s3a 的 merge 以「unrecognized arguments: --attn-mask-tau」中止
- **根因**：遠端只有一個工作目錄而兩個 session 共用。`env.sh` 最後一行是
  `cd $HOME/WACV`，而 merge 分支呼叫 `run_stage.py` 時沒有自己的 `cd`
  ——於是跑到另一條分支的版本
- **為什麼幸運**：只在旗標剛好不存在時才報錯。兩條分支的 CLI 若相容，
  就會安靜地用另一棵樹的程式碼跑完，連 `src` 都會跟著換
  （`sys.path.insert(0, parents[1])`）
- **處置**：`WACV_ROOT` 由腳本自身位置推導；`source env.sh` 之後補
  `cd "$WACV_ROOT"`

## DEF-013 · 監看腳本把 ssh 的 stderr 併入判斷用的取值

- **症狀**：段 0 還在跑就被判成收工並誤報失敗（假警報，未影響實驗）
- **根因**：判斷值走了合併 stderr 的路徑，再用 `tr -dc '0-9'` 抽數字；
  ssh 的警告訊息裡的埠號 `10101` 被抽出來當成計數
- **處置**：判斷用的取值一律丟掉 stderr，並只接受 `K=<整數>` 這個形狀

## DEF-014 · 裁切就地覆蓋資料集，遠端共用工作樹於 `git pull` 時靜默換圖

- **症狀**：s3t30 的 `calib/recon_floor.csv` 與 s3t25 對不上——horse_00
  由 0.1283 變成 0.1581、woman_03 由 0.0878 變成 0.0653。兩批的設計差異
  只有 τ_train，重建下限**不應該**變
- **根因**：`draw_masks.py --recrop` 為 inpainting 產生裁切放大的影像時，
  **就地覆蓋 `data/lo_aligned/`**——那是 img2img 各批（s3a／s3t25／v14／…）
  的資料集。commit 後遠端 `git pull`（basic-1 與 basic-2 共用同一個 NFS
  工作樹 `~/WACV-s3`）把工作樹的影像換成裁切版
- **時序**：s3t25 的分片在 18:15 就把影像載進記憶體，23:05 的 pull 動不了
  它們，故 s3t25 未受影響；s3t30 的段 0 在 23:18 起跑，讀到的是裁切版
- **為什麼難察覺**：兩批都跑得完、格點全部 `done`、報表也印得出數字。
  唯一的線索是重建下限這個與 τ_train 無關的量變了。若不是逐項比對段 0 的
  判讀，這批資料會被當成「τ_train = 0.30 的對照」寫進論文
- **處置**（2026-08-10）：
  1. s3t30 停跑（使用者裁決），`data/lo_aligned/` 由備份逐位元還原，
     以 `git diff f1d32f9a6 -- data/lo_aligned/` 確認 24 張全部回到裁切前
  2. 兩個資料集分開：`data/lo_aligned/`（原圖，img2img，**不得改動**）與
     `data/lo_inpaint/`（裁切版，inpainting）
  3. `--recrop` 改為從 `--originals` 讀、寫到 `--data`，**不就地覆蓋**
  4. `shard.sh` 的 ip profile 帶 `--data data/lo_inpaint`
- **測試**：`test_shard的三個profile` 加驗 `--data data/lo_inpaint`
- **一般化的教訓**：遠端工作樹是共用的，`git pull` 會影響**排隊中**而尚未
  起跑的批次。改動 `data/` 之下任何已被實驗用過的檔案時，要把它當成改動
  `runs/` 一樣看待——舊實驗的輸入是證據的一部分

## DEF-015 · 政策謂詞散在三處，只改其中兩處不會報錯

- **症狀**：無症狀。三處各自寫 `cfg.recon and spec.site == "apa"`——
  `optim_config` 據此把 `align_steps` 歸零、`_train_nonadditive` 據此呼叫
  A 段、`calibrate_lr` 據此跳過階段一的學習率探測
- **後果**：三者必須同進同退。漏改其一的結果是「A 段跑了但階段一也跑了」
  （每格白燒 910 秒）或「跳過探測卻仍索取那個值」（段 1 才以缺鍵中止）
- **處置**：集中為 `executors.uses_stage_a()`，並由測試計算該字串在原始碼中
  出現的次數，防止再被就地展開
- **同型**：逐影像種子 `seed + crc32(image_id)` 也曾寫兩份（`Ra` 的隨機方向
  與投影條件的隨機起點）。兩者必須同分布，否則比較到的差異裡混著起點的差異。
  已集中為 `image_seed()`

## DEF-016 · 參數組由 site 名稱推導，新增 site 時會靜默落回 default

- **症狀**：無症狀
- **根因**：`optim_config` 寫 `"stage2" if spec.site == "apa" else "default"`，
  與本專案「依能力分派、不比對名稱」的慣例相反（`generator.py` 依能力分派、
  `direction_param` 依能力挑成員）
- **後果**：新增一個同樣有兩階段的 site 時漏改，會落回 `default` 而**把兩個
  階段的參數一起更新**——那與設定的兩階段結構是兩件不同的事，且輸出看起來
  完全正常（`stage_parameters` 的 docstring 記的正是這個失效）
- **處置**：改由 `ConditionSpec.train_group` / `align_group` 明寫

## DEF-017 · 隨機起點只加在訓練路徑，段 0 的探測繞過它

- **症狀**：段 0 以「方向參數放大到 2048 倍仍達不到 dists 增量 0.04」中止
- **根因**：投影式條件需要非零的起點（方向參數 V 依 LoRA 慣例初始化為零，
  而**零向量沒有徑向投影**——縮放它到任何倍數都還是零）。起點加在
  `_train_nonadditive` 裡，但模塊有多條建構路徑：段 1 訓練、段 0 的
  `_probe_lr`、量測腳本
- **後果**：同一個缺陷在每一條漏掉的路徑上各出現一次，且錯誤訊息描述的是
  症狀（放大到上限）而非原因（起點為零）
- **處置**：移到共同入口 `build_module`，並在投影器內加零方向的檢查與指路。
  測試以 `inspect.getsource` 釘住位置

## DEF-018 · 投影模式下停止準則永不觸發

- **症狀**：`apa_pj` 三格全部跑滿 250 步上限
- **根因**：`plateau_stop` 要求「某道 hinge 的懲罰為正」才允許停止，理由是
  「還沒被綁住就停 = 停在容量而非極限」。投影把約束變成硬約束後，φ **恆**
  坐在預算球面上，四道 hinge 恆為零——那不是「還沒被綁住」而是「一直被綁得
  剛剛好」，判準分不出這兩者
- **後果**：不是效率問題。跑滿步數上限的格依本專案協議**不可用於跨條件
  比較**，故整輪最貴的三格（4008–4336 秒／格）在證據上是廢的
- **處置**：投影式條件關閉該要求，只看監看量走平。罰項路徑逐位不變並由
  測試釘住兩種模式的行為差異
- **重跑後**：91 / 189 / 110 步正常停止，防禦落差由 −12% 縮到 −4%

## DEF-019 · 跨批複製校準表使「段 0 是否完成」的檢查恆為真

- **症狀**：`apa_tj` 的 train 三格以 `CalibrationMismatch: 鍵
  'stop_tol.edit_shift' 未校準` 全部失敗
- **根因**：為省時間把 `s3t20_pj` 的 `calibration.json` 複製到 `s3t20_tj`，
  而 `shard.sh fanout` 以「該檔存在嗎」判斷段 0 有沒有跑完——**那個檢查因此
  不可能失敗**。複製進去的表只有 pj 的鍵（`lr.N6_stage2`、
  `stop_tol.attn_suppressed`），沒有 tj 需要的 `lr.N7_stage2` 與
  `stop_tol.edit_shift`（兩者的監看量不同）
- **規則**：跨批複製校準表**只在條件集合相同時合法**。沿用同模型設定的批次
  各自再探測自己的鍵是可以的；條件不同就會塞進一個錯的表而檢查看不出來
