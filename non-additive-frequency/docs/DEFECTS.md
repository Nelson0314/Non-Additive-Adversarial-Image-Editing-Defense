# 已知缺陷

只收**會靜默失效**的缺陷——補錯了不會拋錯、輸出看起來正常、但量到的是別的
東西。修好之後仍留在此處，因為同型的錯誤會再犯。

已刪除的方向（注意力抑制、APA 兩階段、位移場）留下的缺陷紀錄一併刪除；
下列各條的教訓仍適用於現行程式。

---

## DEF · argv 太長時 `import onnxruntime` 直接 segfault

- **症狀**：`literature_metrics.py` 跑 270 格時 core dump，跑 60 格的子集
  完全正常。日誌上看起來像「載完模型就死了」。
- **兩層誤導**：
  1. `| tee` 讓 stdout 變成 block buffering，掛掉時最後幾行 `print` 還在
     buffer 裡，於是**日誌顯示的位置比實際早**。加 `-u` 才看得到真的位置。
  2. 加了 `PYTHONFAULTHANDLER=1` 之後才看到 traceback 停在
     `onnxruntime/capi/_pybind_state.py:32`，而當時載入的擴充模組**只有
     numpy 與 PIL**——torch 還沒進來。一度以為是 onnxruntime 與 torch 的
     CUDA runtime 衝突（那是個合理但錯誤的假設），改了載入順序沒有用。
- **根因**：`import onnxruntime` 本身對 **argv 長度**敏感。同一台機器、同一個
  venv 上二分：`--entry` 重複 **270 次可以、400 次必掛**（exit 139）。
  它的 `onnxruntime_pybind11_state.so` 在 `ld.so` 載入時需要 stack 空間，
  而 argv 與 environ 就放在 stack 頂端。真實路徑比測試字串長，所以 270 個
  真實 entry 剛好越過門檻。
- **修正**：清單改由檔案讀（`--entries-file`，一行一個 `label=目錄`），
  argv 恆為常數長度。另在 `_read_entries` 加守門：`--entry` 超過 150 個
  **明確拒絕**並指向 `--entries-file`，而不是讓它去 segfault。
- **不要這樣繞**：縮短路徑或調 `ulimit -s` 只是把門檻往後推，下次擴大批次
  又會踩到，而且症狀是 core dump 不是錯誤訊息。
- **同型**：任何用 `action="append"` 收大量項目的腳本都有這個風險，尤其在
  同一個行程裡還要載 onnxruntime／TensorRT 這類大型 C 擴充時。

## DEF · 探針腳本在 module 層級跑實驗，import 一次就覆寫結果檔

- **症狀**：遠端 `test_every_driver_script_imports` 失敗，
  `FileNotFoundError: runs/carrier_survey/colour_headroom.csv`。本機同一個
  測試通過。
- **根因**：四支探針（`colour_headroom_probe`、`latent_headroom_probe`、
  `make_attack_prompts`、`select_face_candidates`）**整支寫在 module 層級**，
  沒有 `main()` 也沒有 `if __name__` 守衛。那個測試會 import 每一支
  `scripts/*.py`，於是**每跑一次測試就把整個實驗重跑一遍並覆寫結果 CSV**；
  `latent_headroom_probe` 還會順便把 IP2P 的 VAE 權重載進來。
- **為什麼本機看不到**：本機恰好有那些資料檔，所以它「通過」——代價是每次
  測試都在改 `runs/` 底下的結果檔，而那是不可重現的量測記錄
  （`CLAUDE.md` 的資料保全）。**通過比失敗更糟**。
- **證據**：`tests/test_ip2p_run_columns.py` 由 **251 秒降到 6.4 秒**，
  全套由 303 秒降到 140 秒。那個差額就是被重跑的實驗。
- **修正**：四支全部包進 `main()` ＋ `if __name__ == "__main__"`；
  `latent_headroom_probe` 的 VAE 改成延遲載入；寫檔前補
  `out.parent.mkdir(parents=True, exist_ok=True)`。
- **同型**：任何新的 `scripts/*.py` 都必須 import 得進來而不做事。
  那個測試就是守門，不要為了讓它過而放寬它。

## DEF · 位移讀數在抗淨化上給出過度樂觀的圖

- **症狀**：同一批 1440 格，`edit_lpips` 說 JPEG 75 保留 54%、裁切 66%、
  模糊 21%；換成身分讀數（主讀數）是 **12%／4%／1%**。反過來 `quantize8`
  位移說 27%、身分說 93%。兩張表的**排序都不同**。
- **根因**：位移量的是「兩張編輯輸出差多少」，而**淨化本身就會讓輸出改變**，
  那一份與有沒有防禦無關。扣空白地板扣掉的是中位數，不是逐格配對，
  殘留仍然可觀。身分讀數直接問「還認不認得出是誰」。
- **為什麼沒有症狀**：位移的數字看起來完全合理（單調、有梯度、與隨機對照
  拉得開），只是它回答的不是判準那個問題。
- **修正**：**抗淨化的結論一律以身分讀數為準**，位移只作為並列的參考欄。
  兩者一起報，不可只報位移。
- **同型**：這是本專案第四次踩到「代理讀數與判讀相反」——前三次是
  `face_found` 在人眼看得見的臉上誤報、NIMA／CNNIQA 分不出雜訊與印花、
  注意力探測量到的其實是區域面積。**代理讀數必須逐個對主讀數校準過才能用**。

## DEF · 派工的並行度只有設定值的一半，而且不會報錯

- **症狀**：`SLOTS=10`（五卡 × 每卡兩格）的派工腳本，實際只有五格在跑。
  批次照樣跑完、結果照樣正確，**只是慢一倍**。
- **根因**：每一格送出的是 `bash -c "python scripts/ip2p_run.py …"`，
  於是 `ps` 裡有**兩列**含 `ip2p_run.py`——外殼一列、python 一列。
  計數寫成 `ps -u $USER -o cmd | grep -c "[i]p2p_run.py"`，一格被算成兩個，
  `while [ "$(running)" -ge "$SLOTS" ]` 於是在半滿時就停下來等。
- **為什麼沒有症狀**：並行度低不會讓任何一格失敗，也不會出現在任何 CSV 欄位。
  唯一的跡象是「這批怎麼跑這麼久」，而每一批的格數與步數都不同，
  沒有可比的基準。
- **修正**：用 `comm` 欄位把外殼濾掉——
  `ps -u "$USER" -o comm=,cmd= | awk '$1 ~ /^python/ && /ip2p_run\.py/' | wc -l`。
- **同型**：任何用 `bash -c "…"` 包住工作再數 `ps` 的派工腳本都有這個問題。
  數 process 時**一律看 `comm` 而不是只 grep 指令字串**。

## DEF · 上傳清單靠人記得，漏一個檔就在遠端跑舊版

- **症狀**：遠端跑全套測試時 `tests/test_deliver_jpeg.py` 有一個失敗，本機
  同一個檔跑起來 19 項全過。看起來像是新改動打破了什麼。
- **根因**：**本機的那個測試檔改過但沒上傳**，遠端跑的是舊版。逐檔比對
  md5 後發現有 **15 個檔不同步，其中 7 個遠端根本沒有**。
- **為什麼沒有症狀**：`scp` 不會抱怨你少傳了什麼；遠端的舊版程式照樣跑得動，
  只是行為是舊的。同型的事故已經發生過一次——漏傳一支派工腳本，五個新臂在
  遠端一整晚一格都沒跑成。
- **修正**：`scripts/sync_check.sh`，清單由 `git status --porcelain` 產生、
  逐檔比 md5、`--push` 傳完之後**重新比對一次**（`scp` 成功不代表內容相同：
  目標路徑寫錯時它會在遠端建一個沒人讀的新檔而不是報錯）。
- **同型**：那支腳本自己也踩過一次同型的坑——`git status` 印的路徑相對於
  **repo 根**而不是 cwd，沒剝掉前綴時 `[ -f ]` 全部落空，於是它安靜地回報
  「沒有改動」。**比漏傳更糟，因為它看起來是通過的。**

## DEF · 派工腳本用 `GROUPS` 當變數名，指派被 bash 靜默忽略

- **症狀**：`scripts/decoy_sweep.sh` 送出的三個 process 全部立刻死於
  「目錄裡沒有這些組：`['2068']`」。腳本裡寫的是
  `GROUPS="${2:-background collision}"`，明給第二個參數也沒有改變症狀。
- **根因**：`GROUPS` 是 **bash 的內建陣列**，內容是當前使用者的群組 ID。
  指派給它會被**靜默忽略**（不報錯、不設定），`$GROUPS` 展開成主要群組 ID。
  遠端上 `id -g` 就是 2068。
- **為什麼難查**：最小重現（換一個變數名）完全正常，於是看起來像是傳參出錯；
  而 `set -u` 也抓不到——那個變數確實有值。
- **修正**：改名為 `DECOY_GROUPS`。
- **同型**：任何派工腳本都不可用 `GROUPS`、`UID`、`RANDOM`、`SECONDS`、
  `LINENO`、`PWD`、`OLDPWD`、`FUNCNAME`、`BASH*` 當變數名。

## DEF · 同一張卡先後跑兩組誘餌，後一組把前一組的 results.csv 整份重寫

- **症狀**：第二批（`colour_control`）跑起來之後，第一批二十列的
  `runs/ip2p_decoy/dev5/results.csv` 只剩一列。影像檔還在（兩組的條件名不同、
  檔名不撞），只有表沒了。
- **根因**：輸出目錄只按卡號命名（`dev5`），而**每寫一列是整份重寫 CSV**。
  已知的規則是「兩個 process 不可**同時**寫同一個目錄」，這一次是**先後**寫，
  同樣會蓋掉。
- **修正**：目錄名加上組名（`background-collision_dev5`／`colour_control_dev5`）。
- **代價**：第一批的表由版控救回（`runs/` 的 CSV 一律入版控，正是為此）。
- **同型**：任何「每寫一列重寫整份 CSV」的輸出目錄，命名都必須把**這一批的
  全部變因**帶進去，不只是卡號。

## DEF · 補跑時整份工作點清單又送了一次，兩個 process 寫同一個目錄

- **症狀**：`scripts/color_converge.sh` 只為了補跑兩個 `image_guidance` 格
  而重新執行，結果四格全部再送一次，`latent_norm_*` 兩個目錄各有兩個
  process 在寫。
- **根因**：派工腳本沒有「只挑某幾格」的參數。**每寫一列是整份重寫 CSV**，
  兩個 process 寫同一個目錄會互相蓋掉，而且不會報錯。
- **修正**：加上第二個參數（tag 前綴過濾）。這一次在 36 秒內殺掉，
  尚未有任何列寫出。
- **同型**：所有一次送多格的派工腳本都要能只送其中幾格。

## DEF · 半徑被夾到 π，使不同的強度跑出同一組設定

- **症狀**：相位半徑掃描到 θ≥3 之後，失真不再上升。當時判讀為「相位是週期量
  所以有天花板」。
- **根因**：`PhaseParam.set_radius` 寫成 `self.radius = min(r, math.pi)`，
  於是 `--radius 3.5` 與 `--radius 4.5` 建構出**逐位元相同**的模組。天花板
  確實存在，但觀測到的那一段是夾取造成的。
- **修正**：`radius` 本身不封頂，只在傳給 `theta_max` 時封頂。這也讓可學幅度
  增益的上界能跟著 `radius` 走——增益沒有週期性，不該被 π 夾。
- **測試**：`tests/test_param_pgd.py::test_set_radius_clamps_phase_to_pi`
  改為驗證「`radius` 不變、`theta_max` 封頂、`project()` 後 θ 不超過 π」。

## DEF · 由防禦圖反推 DCT 係數來驗證頻帶約束

- **症狀**：驗證「δ 只落在允許的頻帶」時，色度通道判定失敗。
- **根因**：解碼含夾取與 4:2:0 重取樣，AC 的擾動會滲進反推出的 DC 與相鄰
  頻帶。**頻帶約束在像素端根本驗不出來。**
- **修正**：`run_dct_shield` 與 `run_djsma` 直接回傳 δ 本體，測試檢查 δ 而非
  反推值。
- **同型**：任何「先解碼再編碼」的往返都不保值，不可用於驗證編碼域的約束。

## DEF · `_merged` 目錄被自己的 glob 匹配到

- **症狀**：合併分片時輸出目錄被下一輪的 glob 吃回去，列數靜默翻倍。
- **修正**：合併腳本在開頭檢查輸出目錄是否落在來源的 glob 底下，是就拒絕。

## DEF · `env.sh` 把工作目錄換回舊的 repo

- **症狀**：遠端腳本報「找不到資料檔」，而該檔明明存在。
- **根因**：`env.sh` 最後一行是 `cd $HOME/WACV`（舊 repo）。腳本若先 `cd` 到
  新 repo 再 `source env.sh`，工作目錄會被換回去，所有相對路徑指向錯的樹。
- **修正**：**先 `source`，再 `cd`。** 見 [OPERATIONS.md](OPERATIONS.md)。
- **為什麼危險**：兩棵樹的 CLI 若相容，就會安靜地用另一棵樹的程式碼跑完，
  連 `src` 都跟著換。

## DEF · 監看腳本把 ssh 的 stderr 併入判斷用的取值

- **症狀**：批次還在跑就被判成收工。
- **根因**：判斷值走了合併 stderr 的路徑，再用 `tr -dc '0-9'` 抽數字；ssh
  警告訊息裡的埠號被抽出來當成計數。
- **修正**：判斷用的取值一律丟掉 stderr，並只接受明確的形狀。

## DEF · `pkill -f` 的樣式匹配到 ssh 連線本身

- **症狀**：想殺遠端的工作，結果連自己的 ssh session 一起殺掉，輸出被截斷。
- **修正**：樣式用中括號寫法（`[i]p2p_run`），使樣式字串本身不匹配。

## DEF · 政策謂詞散在多處，只改其中一部分不會報錯

- **根因**：同一個判斷條件被就地展開在三個地方。
- **後果**：漏改其一的結果是行為不一致，而輸出看起來完全正常。
- **修正**：集中為單一函式，並由測試計算該字串在原始碼中出現的次數。
- **同型**：逐影像種子也曾寫兩份，兩者必須同分布，否則比較到的差異裡混著
  起點的差異。

## DEF · 參數組由名稱推導，新增位置時靜默落回預設

- **根因**：以 `spec.site == "..."` 比對名稱來挑參數組，與本專案「依能力分派、
  不比對名稱」的慣例相反。
- **修正**：改由設定物件明寫。`src/residual/base.py` 以「能力」而非型別對外
  表達（像素側實作 `pixel_residual`，去噪側實作 `eps_hook`），**新增位置時
  不要依注入位置的名稱寫分支**。

## DEF · 隨機起點只加在其中一條建構路徑

- **症狀**：探測階段以「參數放大到上限仍達不到目標」中止。
- **根因**：需要非零起點的參數化有多條建構路徑（訓練、探測、量測腳本），
  起點只加在其中一條。
- **修正**：移到共同入口 `build_module`，並在投影器內加零方向的檢查。
- **通則**：同一個缺陷會在每一條漏掉的路徑上各出現一次，且錯誤訊息描述的是
  症狀而非原因。

## DEF · 停止準則在硬約束模式下永不觸發

- **症狀**：整輪最貴的格全部跑滿步數上限，依協議不可用於跨條件比較。
- **根因**：停止準則要求「某道約束的懲罰為正」才允許停止。投影把約束變成硬
  約束後，參數恆坐在球面上、懲罰恆為零——判準分不出「還沒被綁住」與「一直
  被綁得剛剛好」。
- **修正**：投影式條件關閉該要求，只看監看量走平。

## DEF · 跨批複製校準表使「前置階段是否完成」的檢查恆為真

- **根因**：以「該檔存在嗎」判斷前置階段有沒有跑完，而該檔是從別批複製來的。
- **規則**：跨批複製校準表**只在條件集合相同時合法**。條件不同會塞進一個錯的
  表而檢查看不出來。

## DEF · `.gitignore` 的 glob 讓 git 停止遞迴

- **症狀**：273 個結果檔被靜默排除在版控外。
- **根因**：`runs/` 區塊裡的一條 `runs/*/**` 讓 git 停止遞迴。
- **規則**：改動 `.gitignore` 的 `runs/` 區塊時，必須用
  `git status --porcelain --ignored` 確認沒有結果檔被排除。

## DEF · Windows 產生的 shell 腳本帶 CRLF

- **症狀**：遠端 bash 報 `set: - : invalid option`、`ambiguous redirect`、
  `syntax error near unexpected token`。
- **根因**：在 Windows 上用 `write_text` 寫檔會把 `\n` 轉成 `\r\n`。
- **修正**：`.gitattributes` 已把 `*.sh` 釘成 `text eol=lf`；寫檔後仍要
  明確 `replace(b"\r\n", b"\n")` 再上傳。

## DEF · `echo ... | while read` 讓迴圈跑在 subshell 裡

- **症狀**：腳本的 `wait` 等不到任何背景工作，主控立刻結束。
- **修正**：改用 here-string（`done <<< "$VAR"`）。

## DEF · 主線驅動整支 import 不進來，而 456 條測試全過

- **症狀**：`python -m pytest -q` 全數通過，但 `scripts/ip2p_run.py` 執行時
  立刻 `ImportError`。全部 GPU 工作都被擋住。
- **根因**：該檔引用 `WatermarkSpec` 與 `run_dct_watermark`，兩者早已改名為
  `DJSMASpec` 與 `run_djsma`。**沒有任何測試 import 這支驅動**，於是重新命名
  沒有在任何地方留下症狀。`dct_wm` 那一支還傳了 `topk`／`block_frac`／`eps`／
  `steps` 四個 `DJSMASpec` 根本沒有的欄位。
- **修正**：`dct_wm` 接到現行的 DJSMA 實作（`saliency="grad"`，因為本威脅模型
  沒有分類器，故 `modified_from_paper` 為真）；parser 抽成 `build_parser()`
  使 CLI 可在不載權重的情況下受測；新增一條測試 import `scripts/` 底下每一

## DEF · cross-attention 的區域比例退化成區域面積

## DEF · 隨機臂的可學張量用了全解析度的形狀，兩個美化旗標對它靜默失效

- **症狀**：`res` ∈ {1,8,16,24,32} 五個設定下，隨機臂渲染出來的圖**逐位元

- **根因**：`PatchRandomParam.reset` 抽噪聲時寫 `torch.rand(x01.shape)`，
  而不是 `torch.rand(self._content_shape(x01))`。可學張量因此恆為全解析度，
  `_field` 的兩步都退化成恆等——`F.interpolate` 是同尺寸的恆等，
  `repeat` 之後的裁切又切回原張量。**兩步都不拋錯。**
- **為什麼難查**：`geometry()` 的 `patch_res` 欄照實寫 16，因為那一欄讀的是
  旗標不是張量；派工腳本的燒測正是查那一欄，**會通過**。
- **後果不是「隨機臂稍微不準」**：帶限批的 `s16_rand` 是那一批的**地板**，
  它退化成 `free` 的隨機臂之後，「最佳化在帶限之下買到了什麼」這個問題會被
  拿一個錯的分母去答。同批的兄弟類 `PatchPaletteRandomParam` 寫的是
  `_content_shape`，兩者的差別只有一個字。
- **影響範圍**：既有的 `runs/` 沒有一列同時是 `patch_rand` 且 `res > 1` 或
  `tile > 0`，故沒有已存的資料受影響。`res=1, tile=0` 時新舊兩式給出相同形狀
  與相同抽樣順序，既有的 `patch_rand` 批次逐位元不變。
- **測試**：`tests/test_patch_res.py` 檔尾五條——形狀縮小、不同 `res` 給不同

- **通則**：**子類覆寫 `reset` 另抽參數時，形狀要走父類的形狀函式，不要重寫
  一個看起來對的。** 同型的檢查是「換一個旗標值，輸出有沒有變」——
  只檢查形狀或只檢查 CSV 欄位都抓不到。

## DEF · 比值型讀數觸到實作的量化地板，而地板隨分母縮小反而上升

- **症狀**：`adverse_cleaner` 在 RMS 0.01 上每個頻率都是 `energy` 0.392，
  讀起來像「留下四成」；振幅再降到 0.004 時變成 0.980，讀起來像「幾乎全留」。
- **根因**：上游 `clean.py` 最後一行 `astype(np.uint8)` 把輸出截斷到一個灰階。
  擾動小於 `bilateralFilter` 的 σ_color = 8 時被完全抹平，
  `P(x+δ) − P(x)` 剩下的只有那一階截斷差，與 δ 無關。量出來的比值因此恰好是
  `1/(RMS·255)`——**與量測值相符到四位有效數字**。
- **為什麼難查**：0.392 是合法值、沒有例外、不隨頻率變（那反而像「乾淨的
  結論」）。而且**方向是反的**：振幅越小、地板越高，讀起來像存活率變好。
- **判別法**：**看 `align`。** 地板上的殘差與擾動無關，`align` 必為 0；
  真正的存活會帶著非零的對齊。此處 RMS ≤ 0.02 的每一格 `align` 都是 0.00。
- **修正**：`scripts/purifier_transfer.py` 加 `quant_floor` 欄，逐格記
  `1/(rms·255)`，出表時要與 `energy` 並看。數值與說明見
  `runs/purifier_transfer/README.md` §七。
- **通則**：任何 `‖輸出差‖ / ‖輸入差‖` 的讀數，在分子接近實作的量化階時失效。
  掃描振幅時要把那個階當成一條線畫在圖上，不要只看比值。

## DEF · 把軟支撐硬化成布林，羽化帶被整條算成滿的而掃描完全沒有作用

- **症狀**：掃 `--carrier-feather` 的 0／8／16／32／48／64 六個寬度，
  **六列的加權面積全部是 0.249、每一個讀數逐位元相同**。
- **根因**：量測程式把支撐寫成 `torch.where(sup > 0, field, x)` 或
  `obj.support = (sup > 0)`。羽化的輸出是 `[0,1]` 的**軟權重**，`> 0` 之後
  整條羽化帶變成滿的，於是「羽化多寬」對輸出完全沒有影響。
- **為什麼難查**：不拋錯、不產生 NaN，六列的數字都是合法值，而且彼此一致
  ——**一致本身看起來像「這個旋鈕沒有用」這個結論**，而不像 bug。
  `PatchParam.render` 走的是混色式子 `(1−w)·x + w·field`，兩條路徑因此分岔。
- **修正**：量測端一律用與 `render` 相同的混色式子，不要自己寫 `where`。
  `scripts/carrier_feather_tradeoff.py` 與
  `scripts/polar_carrier_probe.py::carrier_stage` 都已改。
  改之前 `polar_carrier` 第三節的 `g(φ)` 裁切對齊是 +0.59，改之後是 +0.66。
- **通則**：**任何複製 `render` 行為的量測程式都是一份重複實作。**
  能呼叫 `render` 就呼叫它；非自己寫不可時，混色式子要逐字照抄，
  並且在同一個設定下與 `render` 對過一次數字。
