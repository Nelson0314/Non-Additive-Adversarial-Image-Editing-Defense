## 1. ST-LPIPS 不能當共同約束（判準事前宣告）

### 1.1 為什麼要找替代品

第一階段以 `LPIPS(x_def, x) = τ` 為共同貨幣。但 τ=0.20 上實測到：

| | PSNR | SSIM | DISTS | L∞ |
|---|---|---|---|---|
| 非加性（位移場） | 21.7–23.8 dB | 0.762–0.857 | 0.068–0.074 | 0.68–0.80 |
| 加性（三篇） | 38.1–43.8 dB | 0.984–0.994 | 0.017–0.028 | 0.017–0.197 |

四個指標全部零重疊。「同一個 LPIPS」顯然不對應「同樣的失真」，故去找是否有
指標能公正地通約兩者。

### 1.2 測了什麼、判準是什麼

Ghildyal & Liu，**ECCV 2022**，*Shift-tolerant Perceptual Similarity Metric*
（arXiv:2207.13686，程式碼 `github.com/abhijay9/ShiftTolerant-LPIPS`）。該文
指出 LPIPS 對人眼看不見的微小錯位過度敏感，並以 anti-aliasing 濾波與 pooling
的改造做出對位移寬容、同時仍與人類判斷一致的版本。

**判準（跑之前宣告，見 `scripts/diag_stlpips.py` 的 docstring）**：

- 可採用：兩類的區間**重疊**，或跨類別均值比 < 1.5×
- 不可採用：仍分開 ≥ 2×

在 LPIPS 已被段 2 固定為 0.20 的那一批 `x_def` 上重算（三張圖 × 七個條件）。

### 1.3 結果與裁決

| 指標 | 非加性區間 | 加性區間 | 均值比 | 判定 |
|---|---|---|---|---|
| **ST-LPIPS** | 0.0265–0.0965 | 0.0024–0.0201 | **3.67×** | **不可採用**（分離） |
| LPIPS（段 2 實際使用） | 0.1954–0.2040 | 0.1914–0.2132 | 1.00× | 重疊（本來就被固定） |

原始資料：`runs/v14_merged/stlpips_tau0.2.csv`。

原因可以指認：ST-LPIPS 的寬容度是為**次像素到數像素的全域位移**校準的，
而位移場在 τ=0.20 的 `disp_max` 已是 11.31 px 的**空間變化形變**——那不是
它設計要寬容的對象。

#### 這推翻了 `RESULTS_2026-08-07` §6 的方向

原文寫「以 LPIPS 匹配失真，對非加性方法**不利**」。加上 ST-LPIPS 之後，
**五個獨立指標**（PSNR、SSIM、DISTS、L∞、ST-LPIPS）在同一個 LPIPS 上一致地
把非加性判重 2–46 倍；而使用者的人眼判讀是位移場在 τ=0.20「可見但可接受」、
加性在 43.8 dB「看不見」。

最簡約的解釋不是四個指標都錯，而是：

> **在同一個 LPIPS 上，兩者的人眼可辨失真本來就不相等，非加性明顯較高。**

也就是說 **LPIPS 對齊其實對非加性寬鬆**：我們拿到了更多的可辨預算，
而且仍然輸了。這比原文的說法對結果更不利，但那是資料指向的方向。
**論文若要引用「對齊軸不公平」這個論點，必須改寫成這個方向。**

### 1.4 由此得到的處置

1. **不再找指標。** 沒有純量能讓兩者可通約，因為它們在人眼上本來就不等價
   ——那不是度量的瑕疵，是實情。
2. **LPIPS 維持為運作約束。** 它是文獻標準，且對我們寬鬆；換成一個對自己
   有利的軸反而需要辯護。
3. **報整個向量。** 第三層主張本來就要求「報全部指標不挑選」。
4. **人眼 2AFC 是唯一名副其實的軸**，待使用者有時間時做：對每個條件找出
   「剛好變得礙眼」的振幅，用它當共同約束。

### 1.5 附帶記錄：安裝

`pip install stlpips-pytorch` 另需 `ipython` 與 `torchsummary`（套件未宣告）。
其 `weights/vST0.0/` **只含 shift_tolerant 權重**，沒有 vanilla，故對照改用
專案段 2 實際使用的 `piq.LPIPS`——那也才是「換掉共同貨幣會怎樣」的正確對照。

## 2. 階段一重做（v14r）

### 2.1 變因

| 項目 | 第一階段（v14） | 重做（v14r） | 理由 |
|---|---|---|---|
| **strength** | 0.6 | **0.4** | 攻擊區間在 0.5 飽和、防禦效果在 0.4 後崩掉，0.4 是唯一兩者兼具的點（`RESULTS_2026-08-07` §6c） |
| **tau_acut** | 0.04 | **0.16** | 由 `τ_train=0.20` 依 `0.8 × τ` 導出 |
| **tau_chroma** | 0.8 | **3.2** | 由 `16 × τ` 導出 |
| 其餘 | — | 完全相同 | 模型、解析度、精度、格點、種子 |

只跑 v14（SD v1.4 / 512²）。**不跑 b3**：SDXL 的攻擊在 strength 0.6 的區間
只有 0.038，降到 0.4 會趨近於零，保證沒有訊號。

### 2.2 為什麼重跑段 0 而不複製現成校準表

`Calibration.REQUIRED_CONTEXT` 是 `(model, resolution, guidance, steps, gpu,
precision)`，**不含 `strength`**，技術上可以直接複製 v14 的表省下 4.8 小時。

**但沒有這樣做。** 原本那張表是在 `tau_acut = 0.04` **正在綁定**的情況下
探出來的（第一階段六個訓練格的 `fid_acut` 全部頂在 0.0401–0.0404），而本批
已把該門檻放寬到 0.16。沿用一張在「已不存在的約束」下探出的表，正是本專案
一再吃虧的靜默沿用型態。

> **順帶記錄一個潛在缺陷**：`strength` 不在 `REQUIRED_CONTEXT` 裡，而學習率
> 是**透過該 strength 的編輯鏈**探測出來的。換 strength 而沿用校準表不會
> 觸發 `CalibrationMismatch`。要嘛把 `strength` 加進 `REQUIRED_CONTEXT`，
> 要嘛在每次換 strength 時明確重跑段 0。

### 2.3 執行

```bash
BATCH=v14r bash scripts/shard.sh calib  bird_03 cat_02 dog_03
BATCH=v14r bash scripts/shard.sh fanout bird_03 cat_02 dog_03
BATCH=v14r bash scripts/shard.sh merge  bird_03 cat_02 dog_03
```

`shard.sh` 的 `v14r*` profile 已就緒（commit `17099d5c7`）：與 `v14` 同一組
模型設定，只多 `--strength 0.4`。門檻不必指定，`run_stage` 會由 `--tau-train`
依比例導出並印在 log 上（實測輸出 `[thresholds] tau_acut = 0.16`、
`tau_chroma = 3.2`）。

`v14r*` 必須排在 `v14*` **之前**——bash 的 `case` 取第一個相符者。

### 2.4 狀態（2026-08-08 04:03）

段 0 於 GPU 0 執行中（tmux `wacv-calib`，PID 3031471），格點 3294 格。
預估段 0 約 4.8 h、段 1–3 三卡平行約 7.5 h。

### 2.5 跑完之後要看什麼

1. **`lr.N2` 是否仍落在 0.02–0.1。** 門檻放寬會改變損失地景，探測結果可能
   與第一階段不同——**那正是重跑段 0 的目的**，不要視為異常。
2. **段 1 的 `train.csv`，`fid_acut` 的最大值。** 第一階段是精確頂在 0.0401
   –0.0404。本批若改為頂在 **0.16**，表示約束仍然綁定、只是位置移了；若
   末端 `fid_lpips` 接近 0.20 而 `fid_acut` 明顯低於 0.16，才是真的解開了。
3. **τ=0.20 的 `x_def` 用人眼看過再跑段 3。** 放寬門檻買到的是訓練自由度，
   代價可能是同一個 LPIPS 下的可見失真變差。使用者先前判讀「τ=0.20 可接受」
   是在**受約束的 φ** 上做的，放寬後未必仍成立。這一步很便宜（段 1 約 1 h），
   而段 3 要 7 h，值得先看。

## 3. 共用工作區的風險（操作事項）

2026-08-08 起有**兩個 session 在同一個工作目錄**同時工作（本 session 跑
階段一重做，另一 session 跑階段二 inpainting）。實際遇到的情形：

- 對方的 commit（`672572a48`、`2f7d7f6ac`）出現在本 session 的 `git log` 中；
- 對方**未提交的編輯中狀態**使完整 `pytest` 出現 4 個失敗（侷限於
  `tests/test_inpaint.py`），那不是回歸；
- `shard.sh` 被雙方各自修改（對方改了 calib 的 session 命名，本 session 加了
  `v14r*` profile）。

**處置**：commit 一律用**明確路徑**，不用 `git add -A`——否則會把對方的
半成品掃進自己的 commit。測試門檻改用相關子集
（`tests/test_grid.py tests/test_objective.py tests/test_executors.py`）。

**建議**：兩個 session 各用一個 git worktree，或各用一條分支。共用工作目錄
沒有任何機制能防止互相污染。
