## 2. TF32：E27 的設定被指紋比對確認

換機器後每步成本從 E27 記載的 2.47 s 變成 7.19 s。原因是 TF32：E27 那批跑在
預設開啟的時期，關閉是 E28 才改的（commit `672a39b`）。在同一台 H100 上把
兩種設定都量一次，結果不只是速度：

| | TF32 開 | TF32 關 | E27 實測 |
|---|---|---|---|
| 每步 | 2.36 s | 7.19 s | 2.47 s |
| 每格評測 | 33.7 s | 147.6 s | 41.4 s |
| 峰值顯示記憶體 | 10317 MB | 25119 MB | 10320.2 MB |

峰值記憶體 10317 對 10320 這一項等同指紋：**E27 確實在 TF32 開啟下跑**。
（關閉 TF32 時 cuDNN 改選演算法，工作區記憶體漲到 2.4 倍，這是速度以外的
第二個可觀察差異。）

E29 依使用者決定在 TF32 開啟下跑。依據是 `src/utils/device.py` 自己記載的
範圍：TF32 唯一有記錄的損害是 BDIA 精確反演，而 site C 與 site P 都不走反演，
`e29_calibration.sh` 與 `e30_grid.sh` 也都沒有傳 `--exact_inversion`。
此項寫在每個 `env.json` 的 `tf32` 欄位（`run_defense.py:674`），可查。

## 3. site C 永遠被色度 hinge 綁住，與學習率無關

`NEXT_SESSION` §5 的開跑判準是「每一格的綁定者都必須是 LPIPS hinge」。
六個學習率的結果：

| run | 末 LPIPS（τ=0.05） | 末色度（τ=0.8） | 最佳 shift | LPIPS 啟動 | 色度啟動 |
|---|---|---|---|---|---|
| C lr=0.1 | 0.0258 / 0.0324 | 0.769 / 0.763 | 0.417 / 0.421 | 0/60、0/60 | 23/60、13/60 |
| C lr=0.15 | 0.0348 / 0.0417 | 0.753 / 0.708 | 0.438 / 0.435 | 0/60、0/60 | 37/60、18/60 |
| C lr=0.2 | 0.0386 / 0.0387 | 0.741 / 0.803 | 0.426 / 0.406 | 0/60、0/60 | 44/60、25/60 |
| C lr=0.3 | 0.0494 / 0.0484 | 0.815 / 0.864 | 0.426 / 0.429 | 8/60、0/60 | 56/60、41/60 |
| P lr=0.03 | 0.0531 / 0.0509 | 0.366 / 0.298 | 0.400 / 0.440 | 11/60、13/60 | 0/60 |
| P lr=0.1 | 0.0447 / 0.0566 | 0.348 / 0.272 | 0.384 / 0.399 | 36/60、44/60 | 0/60 |

四個學習率涵蓋 3 倍範圍，site C 全部由色度 hinge 綁住，LPIPS hinge 最多啟動
8/60 步。**綁定者是這個參數化的性質，不是學習率的性質**——site C 的作用機制
就是改色度矩陣，把色度偏壓約束在 0.8 就是約束它的全部容量。

`NEXT_SESSION` §5 預先寫下了兩種可能，這裡可以逐項對照：

- 「末色度隨 shift 一起塌掉，防禦能力歸零換來合規」——**沒有發生**。
  lr=0.1 的 shift 0.417／0.421 與 site P 的 0.400／0.440 相當。
- 「降 lr 後 LPIPS hinge 接手」——**沒有發生**，六個學習率都沒有。

## 4. 否定結果：編輯沒有被擋下來

### 4.1 影像

`runs/e29_edit_page/car_00_compare.png`、`car_01_compare.png`（τ=0.05、60 步）
與 `runs/e29c_edit_page/car_00_compare.png`（τ=0.10、150 步上限、平台停止）。
上排是防禦圖，下排是同一張圖被 `a wrecked car after an accident` 編輯之後。

每一張下排影像都長出了 prompt 要求的毀損車輛，包含沒防禦的對照與全部防禦
版本。要判斷的是「prompt 的內容有沒有發生」，不是「兩張圖像不像」——兩次
擴散輸出即使都達成 prompt 也本來就不同。

**這些圖用的是防禦訓練時見過的那個 ε。** `e29_edit_page.py` 的 `--seed`
預設 20260728 等於 `OptimConfig.seed`，而 `optimize.py:377` 的訓練雜訊是
`sample_edit_noise(cfg.seed + i)`，i=0 那一個與此逐位元相同。這是對防禦
**最有利**的條件，換未見過的 ε 只會更差。

保真度那一側同時可見：site P 的防禦圖與原圖幾乎分不出來，site C 兩個學習率
在白色車身與窗框上都有可見的綠紫色偏。這順帶確認了 E28 由人眼定出的
τ_chroma = 0.8 抓得準——色度偏壓 0.74–0.86 確實在可見的邊緣上。

### 4.2 語意軸（正式判準）

E25 §1.1 確立 SigLIP 為判準（CLIP 未通過自身對照）。`e29c` 的
`results.csv`，`purify=identity` 即未經淨化的乾淨攻擊：

| | 未防禦編輯 | 防禦後編輯 | 差 |
|---|---|---|---|
| site C τ=0.10 | 0.1202 | 0.1068 | −0.0134 |
| site P τ=0.10 | 0.1202 | 0.1277 | **+0.0075** |

site C 使服從度下降 11%，site P 使它**上升**。兩者都不構成阻擋。

### 4.3 與 `edit_shift` 的對照

同一批資料的 `edit_shift` 是 0.42（C）與 0.47（P），margin=1.0 從未飽和，
數字看起來像是「輸出被推開很多」。影像與語意軸都說編輯照常發生。

這是本專案第三次量到同一件事：E25 在 726 格中語意失敗 0 格、E26 找出攻擊端
根本沒有 CFG、E29 在修好 CFG 之後仍然如此。**`edit_shift`／`net_lpips` 量的是
輸出移動了多少，不是編輯有沒有失敗。**

## 5. 邏輯稽核：實驗設計與研究歷史的衝突

E30 沒有跑，不是因為機時或校準，而是因為下列兩項。兩項都不是這一輪的新發現
——它們都寫在 `docs/RESULTS_E25-E26.md` §6 的待決清單裡，而後續三個實驗
（E27 校準、E28 色度約束、E29 校準）處理的都是清單上的其他項目。

### 5.1 目標函數最大化的，正是已被判定不對應防禦成功的那個量

`objective.py:348-352` 的 `untargeted` 模式：

```
L_def = mean_i max(0, margin − LPIPS(y_def_i, y_orig_i))
```

即**最大化「防禦圖被編輯的結果」與「原圖被編輯的結果」之間的 LPIPS 距離**，
上限 margin。那正是 `edit_shift`。

而 E25 §1.2 的結論是：這個量與編輯是否失敗不對應（726 格語意失敗 0 格）。
E25 之後判準改成了語意軸，**目標函數沒有跟著改**。於是 E27、E28、E29 都在
最大化一個已知不對應目標的量，並打算用另一個量來評分。

兩張都達成 prompt 的擴散輸出，彼此的 LPIPS 距離本來就可以很大。把它推到
0.42–0.47 不需要讓任何一張停止服從 prompt。這在數學上沒有矛盾，是目標與
判準本來就是兩個不同的量。

### 5.2 失真預算比文獻低 5–8 倍

E25 §6 第 6 項已經量過並列出：本專案的運作點 `defimg_lpips` 為
0.036–0.059，而 DCT-Shield（ICCV 2025）自報 LPIPS 0.267，PhotoGuard／MIST／
AdvDM／SDS／DiffusionGuard 為 0.284–0.362。E29c 實測本輪運作點是
0.0386（site C）與 0.0856（site P），差距不變。

τ 的三個值 0.02／0.05／0.10 全部落在文獻運作點的十分之一到三分之一。在這個
預算下觀察到「防禦無效」，無法區分兩種解釋：

1. 這個方法無效；
2. 任何方法在這個失真預算下都無效。

現有資料不能分辨這兩者，因為從未在文獻的預算區間量過。

### 5.3 E25 §6 六項待決，做了 1–4，沒做 5 和 6

| 項 | 內容 | 狀態 |
|---|---|---|
| 1 | 以 w=7.5 重跑 | E29 已做 |
| 2 | 判準改語意軸 | E25 已做，`e27_report.py` 已依此撰寫 |
| 3 | site C 的四臂探針 | E28 已做（P9） |
| 4 | site C 的 `max_dev` 校準 | E27 已做 |
| 5 | **targeted 與 suppress 兩個目標的實測** | **未做** |
| 6 | **失真預算提高到文獻區間** | **未做** |

做掉的四項都屬於「把量測與校準弄對」，未做的兩項都屬於「決定防禦能不能
成立」。E29 的否定結果落在後者的射程內。

### 5.4 三個 defense_mode，只有一個被跑過

`runs/` 的 73 個 `env.json` 中有 59 個記錄了 `defense_mode`（其餘 14 個早於
該欄位加入），**全部是 `untargeted`**，共 113 處，無一例外。E25 §4.2 獨立
清點過 4882 列 `results.csv`，同樣 100%。

另外兩個模式都已實作並有測試覆蓋，也都在 tiny-SD 上跑通過，但從未在真實
SD 上產生任何資料：

- `targeted`（`objective.py:341-347`）：最小化與指定目標影像的距離。
  `objective.py` 自己的註解就寫了「無目標最大化在文獻上一貫比有目標脆弱」。
- `crossattn` / `attn_mode="suppress"`（`attention.py`）：最小化內容 token
  分到的注意力質量。這是三者中唯一直接對著「讓編輯不服從 prompt」的目標。

## 6. 稽核中沒有發現問題的部分

列出來是為了讓下一輪不必重查：

- **雜訊的訓練／保留分離是做對的。** `run_defense.py:165-166` 以
  `EVAL_SEED_OFFSET = 10000` 取未見過的種子，並以 `noise_split` 欄位區分，
  兩者併列報告。噪聲過擬合是被量測的，不是被忽略的。
- **三道保真約束彼此不循環，各擋一種失效。** E28 §3 已驗證。E29 的影像
  再次確認 τ_chroma = 0.8 的人眼定錨是準的。
- **綁定者診斷工具正確。** `e27_binding_check.py` 在補上色度那一道之後
  （commit `7573ff1`）判定與 `history.json` 一致，E29 的六個學習率給出
  彼此連貫的趨勢。
- **防禦 hinge 沒有飽和。** margin=1.0 下全部格子 0/60 飽和，防禦項自始至終
  都有梯度。「防禦沒發展起來」不是因為目標被夾住。
- **兩條分支共用同一個 ε。** `sdedit` 以介面強制，E29 的影像亦然。觀察到的
  差異不來自抽樣。

## 7. 這一輪確立的事

1. 在 τ ≤ 0.10 的失真預算下，`untargeted` 目標對 stock SD v1.4 的
   SDEdit（w=7.5、strength=0.5）**沒有防禦效果**，加性與非加性皆然。
   證據是影像與 SigLIP 兩者一致，且是在對防禦最有利的雜訊條件下量的。
2. site C 的綁定者恆為色度 hinge，與學習率無關。這是參數化的固有性質。
3. E27 的成本基準是在 TF32 開啟下量的，此事實由三個數字的指紋比對確認。
4. 目標函數與判準是兩個不同的量，而目標函數最大化的那一個已被 E25 判定
   不對應防禦成功。這是本輪未能得到正面結果的最可能原因，且與失真預算
   偏低這一項互相獨立。
